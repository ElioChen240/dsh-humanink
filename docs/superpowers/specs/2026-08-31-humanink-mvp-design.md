# HumanInk 通用中文内容工作台 MVP 产品文档

- **产品名称**：HumanInk
- **产品形态**：DeepSeek Harness 插件
- **文档版本**：0.1.0
- **文档状态**：已确认，待实现
- **编写日期**：2026-08-31
- **首期范围**：通用中文自媒体内容，不绑定单一发布平台

## 1. 产品概述

### 1.1 一句话定位

> 给创作者一个想法、标题或素材，HumanInk 帮其完成选题、标题、写作、人味化和发布前复核，最终输出一份可编辑、可追踪、可导出的中文内容。

### 1.2 要解决的问题

中文自媒体创作者通常需要在以下环节之间来回切换：

1. 判断一个想法是否值得写；
2. 找到适合的内容角度；
3. 起一个有吸引力且能被正文支撑的标题；
4. 组织文章结构和素材；
5. 将初稿改得自然、具体、有个人表达；
6. 检查事实、重复、空泛和模板化表达；
7. 留存版本并导出最终内容。

HumanInk 将这些零散动作组织为一条可暂停、可编辑、可重试的内容生产流程，而不是一次性生成一篇黑盒文章。

### 1.3 核心价值

- **像作者本人**：通过创作者档案和真实素材保留个人语气、经历与判断。
- **像中文内容**：针对中文 AI 写作中的模板化、宣传式、空泛和过度工整表达进行诊断与处理。
- **可控可回退**：原文、初稿、改写稿和用户修改均保留版本。
- **可检查再发布**：使用 HumanInk 规则检查，并可选调用腾讯朱雀进行外部参考检测。
- **可扩展交付**：核心业务与 DeepSeek Harness、模型、搜索和图片服务解耦。

## 2. 产品原则

### 2.1 人味不是伪装

“去 AI 味”在 HumanInk 中定义为提升自然度、具体性、个人表达和中文语感，不定义为绕过 AI 检测器。产品不得提供“循环改写直到检测分数低于某个阈值”的功能，也不得承诺检测结果代表作者身份或文章来源。

### 2.2 真实优先于完整

当文章需要个人经历、数据或事实，而输入素材不足时，系统必须提出补充问题、标记不确定性或改为非第一人称表达，不能擅自编造。

### 2.3 标题负责吸引，正文负责兑现

标题生成必须同时给出标题策略、吸引点、风险和正文支撑要求。标题不能以夸张承诺换取点击，也不能与正文内容脱节。

### 2.4 AI 提速，作者决策

每个阶段都允许用户编辑、确认、跳过和重试。AI 的建议不能静默覆盖用户输入，最终发布由用户决定。

### 2.5 证据和版本可追踪

外部资料、检测结果和生成结果都要关联到具体内容版本；任何检测或改写结果都不能脱离版本单独显示。

## 3. 参考项目和借鉴边界

### 3.1 Humanizer-zh

Humanizer-zh 是本产品中文人味化能力的重要参考。它整理了多类中文 AI 写作模式，并通过诊断、针对性修改和复核来处理空泛概括、宣传式表达、过度排比、填充短语等问题。

HumanInk 借鉴其以下思想：

- 将“AI 味”拆成可识别的问题模式；
- 先找问题片段，再进行局部修正；
- 保留核心含义和原有语气；
- 用具体细节、真实判断和自然节奏提升表达；
- 输出修改说明，而不是只给一篇新文章。

HumanInk 不直接把外部项目作为运行时依赖，也不把一个 Skill Prompt 当成完整产品。若未来复用其代码、文字或规则文件，必须先确认并遵守原项目许可证和署名要求。

### 3.2 腾讯朱雀 AI 检测

朱雀检测作为发布前的外部参考层。它不能成为写作主流程的硬依赖，也不能被包装成“真人/AI”的绝对判定。用户必须主动发起检测，页面需要说明内容会提交至外部服务。

朱雀结果仅用于：

- 标记需要人工复核的段落；
- 帮助用户发现仍然模板化或缺少个人内容的部分；
- 记录某个文章版本的外部检测参考结果。

不用于：

- 自动判定文章是否可以发布；
- 自动循环改写以降低检测值；
- 宣称文章一定由人类创作；
- 替代原创性、事实和版权检查。

## 4. 目标用户和使用场景

### 4.1 首期目标用户

- 个人自媒体创作者；
- 需要稳定产出中文文章的运营人员；
- 有真实经验但不擅长组织文字的专业人士；
- 使用 AI 生成初稿、但不满意成文质量的创作者。

### 4.2 首期不绑定的平台

MVP 不针对微信公众号、小红书、抖音、知乎等任一平台做专属规则。文章输出采用通用 Markdown、HTML 和纯文本，平台长度、标签和发布接口放入后续版本。

### 4.3 典型场景

#### 场景 A：从一个想法开始

用户输入一个模糊想法，HumanInk 生成选题卡、内容角度、标题候选和写作提问，用户确认后生成文章。

#### 场景 B：从一个标题开始

用户输入标题，HumanInk 判断标题承诺、提供多种标题策略，生成内容简报、大纲和初稿。

#### 场景 C：改写现有内容

用户粘贴一段文章，HumanInk 识别模板化表达，提供轻度润色、标准人味化或深度重构，并展示改写前后对比。

#### 场景 D：发布前复核

用户选定一个文章版本，运行 HumanInk 检查和朱雀检测，查看需人工确认的段落后再导出。

## 5. MVP 目标和边界

### 5.1 MVP 目标

验证以下闭环是否能够稳定完成：

```text
一个想法或标题
  -> 内容角度
  -> 标题方案
  -> 内容简报
  -> 文章大纲
  -> 文章初稿
  -> 中文人味化
  -> 发布前检查
  -> 朱雀检测参考
  -> 版本化导出
```

### 5.2 MVP 必须实现

1. 内容项目和文章编辑；
2. 创作者档案 Lite；
3. 基于输入的选题建议；
4. 标题实验室；
5. 内容简报和文章大纲；
6. 文章初稿生成；
7. 中文人味化引擎；
8. 改写前后对比和修改说明；
9. 发布前质量检查；
10. 朱雀检测适配和结果展示；
11. 内容版本管理；
12. Markdown、HTML、TXT 导出；
13. DeepSeek Harness 插件入口；
14. 本地可重试、可恢复的任务状态。

### 5.3 MVP 明确不实现

- 实时全网热点抓取；
- 自动搜图和图片版权聚合；
- AI 封面生成和模板排版；
- 平台专属格式和自动发布；
- 社交账号登录；
- 标题点击率和内容数据分析；
- 团队协作、计费和多租户；
- 以规避 AI 检测为目标的自动循环改写。

MVP 可以为图片和实时搜索保留 Provider 接口，但不因这些外部能力阻塞文字内容闭环。

## 6. 功能需求

### 6.1 内容工作区

#### 功能

用户可以创建、编辑、保存和导出一个内容项目。

#### 项目字段

```text
项目名称
原始想法
目标读者
写作目标
已有素材
目标篇幅
当前文章版本
当前任务状态
创建时间
更新时间
```

#### 要求

- 用户输入自动保存；
- 原始内容永不被生成结果覆盖；
- 每次生成产生独立版本；
- 生成失败保留已有内容；
- 文章可复制、编辑、恢复历史版本；
- 运行中任务显示状态和取消入口。

### 6.2 创作者档案 Lite

#### 字段

```text
身份或职业
长期写作主题
目标读者
常用语气
期望篇幅
常用开头方式
常用案例
不喜欢的表达
个人补充说明
```

#### MVP 要求

- 支持新增、编辑和清空；
- 生成文章前可以查看本次会使用的档案摘要；
- 用户可以对某次任务临时覆盖风格；
- 不把创作者档案写入公开导出文章，除非用户主动选择。

### 6.3 选题建议

#### 输入

```text
主题关键词
创作者领域
目标读者
已有经历
希望表达的问题
```

#### 输出

每次生成 5 个选题卡：

```text
选题名称
核心问题
目标读者
内容价值
推荐切入角度
可能形成的观点
建议标题
需要的真实素材
写作难度
时效性说明
```

MVP 的选题建议基于用户输入、创作者档案和本地已有内容，不承诺实时热点。实时搜索放入后续 Provider。

### 6.4 标题实验室

#### 输出策略

- 观点型；
- 冲突型；
- 故事型；
- 结果型；
- 悬念型；
- 清单型；
- 稳妥型；
- 搜索友好型。

#### 每个标题包含

```text
标题文本
标题策略
吸引点
目标读者
潜在风险
正文需要支撑的内容
推荐程度
```

#### 验收要求

- 一次至少生成 6 个候选标题；
- 候选标题策略不应全部相同；
- 标题中的数字、承诺和范围需要在正文生成前被记录；
- 正文生成后检查标题承诺是否被正文支撑；
- 用户可以选择一个标题作为当前版本的主标题。

### 6.5 内容简报和大纲

#### 内容简报

```text
写给谁
解决什么问题
核心观点
次级观点
文章情绪
不能编造的内容
需要用户补充的事实
建议使用的案例
```

#### 大纲

```text
开头钩子
第一部分
第二部分
第三部分
结尾观点
行动建议
```

用户确认大纲后才能进入正式初稿生成；用户也可以跳过确认，但系统要记录为自动确认。

### 6.6 文章初稿生成

#### 输入

```text
标题
内容简报
大纲
创作者档案
用户补充素材
目标篇幅
```

#### 输出

```text
文章标题
导语
正文
结尾
待确认信息
引用或来源占位
```

#### 生成约束

- 不虚构个人经历；
- 不虚构数字、引用和案例；
- 不把推测写成事实；
- 不用标题无法支撑的夸张承诺；
- 不强制套用“首先、其次、最后”；
- 不连续使用格式化总结句；
- 不以“希望本文能够帮助你”等空泛句式填充结尾；
- 素材不足时列出问题，不默认为真实。

### 6.7 中文人味化引擎

#### 处理流程

```text
原文
  -> 问题片段识别
  -> 模式归类
  -> 修改建议
  -> 受约束改写
  -> 含义和保护字段复核
  -> 输出对比结果
```

#### MVP 模式

**轻度润色**：修复语病、调整节奏、删除明显套话，尽量保留原句。

**标准人味化**：处理空泛大词、宣传式表达、过度整齐、重复和翻译腔，补充用户提供的具体内容。

**深度改写**：重组段落、重写开头、增强观点、调整叙事顺序，但不凭空增加经历或事实。

#### 诊断输出

```text
问题类型
原文片段
问题说明
修改建议
是否需要用户补充
修改后的片段
```

#### 保护字段

用户可以锁定以下内容，改写不能静默修改：

- 数字；
- 日期；
- 人名和地名；
- 产品名和专有名词；
- 引用；
- 链接；
- 用户手动标记的句子。

#### 结果要求

人味化结果必须同时提供：

1. 改写后的全文；
2. 主要问题摘要；
3. 修改前后对比；
4. 未解决的不确定性；
5. 用户需要确认的内容。

### 6.8 发布前质量检查

#### 检查项目

**结构检查**

- 开头是否快速进入主题；
- 标题是否被正文支撑；
- 是否存在重复段落；
- 是否有结构断层；
- 结尾是否突然或空泛。

**表达检查**

- 空泛概括；
- 宣传式表达；
- 过度排比；
- 模板化连接词；
- 翻译腔；
- 无意义总结；
- 段落过长；
- 连续相同句式。

**可信度检查**

- 未核实数字；
- 缺少来源的事实；
- 未确认的个人经历；
- 推测性表达未标记；
- 可能泄露隐私的内容。

#### 输出

```text
检查状态
高优先级问题
中优先级问题
低优先级建议
需要用户确认的事实
推荐下一步操作
```

MVP 不把检查结果压缩成一个看似客观的总分，优先输出可以直接操作的问题列表。

### 6.9 朱雀 AI 检测

#### 用户入口

文章项目中提供：

```text
检测当前版本
```

Harness 命令提供：

```text
/humanink detect
```

#### 检测范围

MVP 仅检测当前整篇文章版本，不做后台自动检测，不做自动循环检测，不做选中段落检测。

#### 检测流程

```text
用户主动点击检测
  -> 检查是否已配置朱雀服务
  -> 提交当前文章版本
  -> 记录任务状态
  -> 接收结果
  -> 关联当前内容版本
  -> 展示整体和段落参考信息
```

#### 页面展示

```text
朱雀检测：已完成
检测性质：参考性结果
文章版本：v4
检测时间：2026-08-31 14:32
需要关注：2 个段落

[查看检测段落]
[重新检测当前版本]
```

如果 API 返回整体倾向值，使用“参考值”或“生成倾向”表达，不使用“通过/不通过”“真人/AI”等绝对标签。

#### 段落级展示

```text
第 2 段：建议复核
原因：表达较规整，具体场景不足

第 5 段：建议补充
原因：结论较抽象，缺少个人判断
```

检测结果不能自动触发人味化。用户可以根据报告回到指定段落手动修改或主动发起一次局部改写。

#### 外部服务和隐私要求

- 检测只能由用户主动发起；
- 页面明确提示文章会提交给外部服务；
- API Key 放在 Harness 配置或环境变量中；
- 不将文章原文写入运行日志；
- 不在无 API Key 时伪造检测结果；
- 服务不可用时不影响保存、改写和导出；
- 检测结果必须标记 Provider、时间和文章版本；
- 原文和检测结果可由用户删除。

#### 失败状态

```text
not_configured
running
succeeded
failed
timeout
cancelled
```

失败时显示具体原因和重试入口，已有文章内容保持不变。

### 6.10 版本管理和导出

#### 版本类型

```text
原始内容
AI 初稿
人味化版本
用户修改版本
检测版本
最终导出版本
```

#### 导出格式

- Markdown；
- HTML；
- TXT；
- JSON 内容包。

检测报告默认不混入纯文章正文，可以单独导出“文章 + 发布前复核报告”。


### 7.3 错误处理

用户应能区分：

- 输入不足；
- 模型不可用；
- 朱雀未配置；
- 外部服务超时；
- 结果格式错误；
- 用户主动取消。

错误信息必须包含下一步建议，不能只返回“请求失败”。

## 8. 技术架构约束

### 8.1 分层

```text
DeepSeek Harness Plugin
  -> Plugin Adapter
  -> HumanInk Core
  -> Humanize Rules
  -> Provider Adapters
  -> Local Storage
```

### 8.2 Plugin Adapter

职责：

- 通过 Harness 插件入口注册命令和工具；
- 注入 LLM、搜索、存储和检测服务；
- 将用户输入转换为核心服务请求；
- 将核心服务结果转换为 Harness 可展示的结构化结果；
- 管理任务状态和错误边界。

### 8.3 HumanInk Core

职责：

- 内容项目；
- 创作者档案；
- 选题；
- 标题；
- 内容简报；
- 初稿；
- 人味化；
- 质量检查；
- 版本管理；
- 导出。

核心层不能依赖具体的 Harness UI，也不能把全部业务逻辑放进 Prompt。

### 8.4 Provider Adapter

首期接口至少包括：

```text
LLMProvider
StorageProvider
DetectionProvider
```

后续扩展：

```text
SearchProvider
ImageSearchProvider
ImageGenerationProvider
```

朱雀只通过 `DetectionProvider` 接入。这样测试时可以使用 Mock Provider，生产环境再使用官方 API 配置。

### 8.5 本地存储

MVP 使用本地存储，优先支持 SQLite 或结构化文件。内容、版本、任务和检测结果分开保存，并通过 ID 关联。

建议实体：

```text
CreatorProfile
ContentProject
ContentVersion
GenerationRun
ReviewFinding
DetectionRun
ExportRecord
```

### 8.6 任务可靠性

每个外部调用必须具备：

- 请求 ID；
- 开始和结束时间；
- 超时控制；
- 有限重试；
- 取消状态；
- 原始输入引用；
- 结果版本关联；
- 可读错误。

外部服务失败不能丢失用户内容，也不能生成无法追溯的“半成品最终稿”。

## 9. 质量和验收标准

### 9.1 功能验收

#### 从标题到文章

```text
输入标题
  -> 生成标题策略或备选标题
  -> 确认内容简报
  -> 生成大纲
  -> 生成初稿
  -> 人味化
  -> 发布前检查
  -> 朱雀检测
  -> 导出
```

#### 从现有内容到改写

```text
粘贴原文
  -> 选择改写模式
  -> 识别问题片段
  -> 输出改写结果
  -> 展示差异
  -> 保存新版本
```

#### 数据安全

- 原文不被覆盖；
- 版本可恢复；
- 检测失败不影响文章；
- 运行日志不包含完整正文；
- API Key 不写入文章和提交记录。

### 9.2 人味化验收

- 能识别至少一组常见中文模板化表达；
- 改写结果保留文章核心观点；
- 锁定字段不被静默修改；
- 输出具体修改说明；
- 素材不足时提出问题而不是编造；
- 轻度模式不会无故重写全文；
- 深度模式仍然保留用户明确提供的事实。

### 9.3 朱雀检测验收

- 未配置检测服务时显示明确的未配置状态；
- 配置正确时能够提交当前文章版本；
- 结果与正确的内容版本关联；
- 页面展示整体摘要和段落级参考信息；
- 检测失败时可重试；
- 检测结果不会被误标为“真人认证”；
- 不会因为检测结果自动改写或自动发布。

### 9.4 工程验收

- 核心服务可脱离 Harness 做单元测试；
- Provider 有 Mock 实现；
- 关键流程有集成测试；
- 正常失败和超时路径均有测试；
- 干净环境能够安装和启动插件；
- 有最小配置示例和故障排查文档；
- 提交前执行 `git diff --check` 和项目测试；
- 提交后工作区保持干净。

## 11. 风险和应对

| 风险 | 应对方式 |
|---|---|
| Harness 预览版 API 变化 | 使用独立 Plugin Adapter，核心层不依赖 UI 内部实现 |
| 模型生成幻觉 | 保护字段、事实占位、用户确认和发布前检查 |
| 人味化过度改写 | 轻度/标准/深度模式、差异对比、版本恢复 |
| 检测误判 | 只展示参考结果，不做绝对结论，不自动阻止发布 |
| 朱雀服务不可用 | DetectionProvider 隔离，失败不影响文本工作流 |
| 外部内容隐私 | 主动触发、明确提示、脱敏日志、配置不入库 |
| 图片版权风险 | 图片能力后置，必须保存来源和许可信息 |
| 功能范围过大 | MVP 只做中文文字闭环，不绑定平台 |

## 12. MVP 完成定义

当以下条件全部满足时，HumanInk MVP 才算完成：

1. 用户可以从一个想法或标题创建内容项目；
2. 用户可以生成并编辑标题、简报、大纲和文章；
3. 用户可以使用三种人味化模式；
4. 用户可以查看改写差异和未解决问题；
5. 用户可以运行发布前质量检查；
6. 用户可以主动运行朱雀检测并查看结果；
7. 朱雀不可用时，文章仍可保存、改写和导出；
8. 每次生成和检测都关联明确版本；
9. 用户可以恢复原文和历史版本；
10. 用户可以导出 Markdown、HTML 和 TXT；
11. 关键成功、失败、超时和取消路径有测试；
12. 插件可以在干净环境中安装、配置和启动；
13. 有完整的安装说明、配置说明、使用示例和故障排查说明；
14. 完成一次 Git 提交，提交信息、版本号、自测结果可追踪。

## 13. 结论

HumanInk MVP 的核心不是“功能最多”，而是完成一个稳定的中文内容闭环：

```text
理解创作者
  -> 帮创作者找角度
  -> 帮创作者写初稿
  -> 帮创作者去模板化
  -> 帮创作者发现风险
  -> 让创作者保留最终决定权
```

第一阶段先把文字生产、人味化、质量复核、朱雀检测和版本导出做稳；搜图、AI 封面、平台适配和数据闭环在核心流程稳定后再加入。
